# Inspect an existing Supabase project safely — future authorized work

This is a runbook, not authorization to connect. No steps were executed during Milestone 1B. Get explicit permission for the named project and scope before using any dashboard, SQL editor, API or database connection. Do not infer the project from a local URL or credential. Never paste credentials, connection strings, customer records or tokens into Git, logs or chat.

1. Have the project owner confirm organization, project reference, environment (production/staging), region, PostgreSQL version, maintainers, billing constraints and authorized inspection role. Stop on any mismatch. Inventory who owns backups and incident recovery.
2. Prefer existing documentation and dashboard configuration views first. Record schema names, exposed Data API schemas, extensions, Auth configuration, Storage policies, Realtime publications, webhooks, scheduled jobs, existing migrations and deployment process. Do not change toggles or run generated SQL suggestions. Do not install/link a CLI, pull/push migrations, reset, seed or create a project as part of inspection.
3. If database catalog inspection is approved, use a least-privileged read-only connection over verified TLS, kept outside the repo. Begin an explicit READ ONLY transaction with short statement and lock timeouts. Inspect metadata only; avoid customer data, function bodies containing embedded credentials, and expensive full-table counts. End with ROLLBACK. Do not call application functions during inspection; SELECT can invoke side effects through functions, so limit queries to the reviewed catalogs below. A read-only transaction is an additional guard, not a replacement for permissions.
4. Review these catalog sources with the authorized administrator: pg_namespace, pg_class (owners, relrowsecurity, relforcerowsecurity), pg_attribute, pg_constraint, pg_indexes, pg_policies, information_schema table/column privileges, pg_default_acl, pg_roles (without password catalogs), and pg_proc metadata (owners, security-definer flags, search-path settings, ACLs). Separately audit function bodies through a secure owner review. Inspect role inheritance, schema CREATE/USAGE, sequence grants, ownership, BYPASSRLS and existing policies, including permissive policy OR behavior. Record object names and risk summaries rather than sensitive definitions. Inspect migration-history metadata only if the existing migration process and history schema are confirmed.
5. Compare every proposed object name (eight public tables, app_private schema/function, indexes, policies) with existing objects and dependencies. These migrations deliberately use plain CREATE to fail on conflicts; never add IF NOT EXISTS to hide incompatible tables. Do not adopt an unknown table, rename/drop objects, disable RLS, rewrite history, or run a repair/reset command. Stop and produce an additive reconciliation plan if anything exists or differs. Confirm gen_random_uuid, auth.users, auth.uid and required Supabase roles exist. Review existing default column grants as well as table grants; table-level REVOKE does not clear independently granted column privileges on preexisting tables.
6. Confirm recoverable backup coverage, retention, restoration ownership and an actual restore rehearsal in an approved isolated environment. Check whether backup coverage includes Auth/Storage assets separately; do not assume database backups cover uploaded files. Record expected data sizes, migration locks, maintenance needs and a forward-fix plan. Never test restoration over the live project.
7. Report the inspected project reference, metadata-only scope, conflicts, privileged access paths, missing backups and proposed reconciliation. Obtain separate explicit approval for a reviewed migration plan only after local runtime RLS tests, staging rehearsal, backup verification and operational workflow review pass. Applying migrations is outside this inspection runbook and this milestone. No cloud apply/reset command is provided here.

The initial migrations create new objects inside transactions and revoke grants before committing. Apply them in timestamp order through the project's established migration process only in a later authorized phase. An interruption after the first migration leaves the new tables closed to application roles. Existing unrelated cloud tables/functions are outside these migrations and require their own security review. No production rollback SQL is provided because dropping tables could destroy data.
